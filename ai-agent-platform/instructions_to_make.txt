5. Why we need our own social_accounts table

Never make your application depend on querying SocialAPI every time.

For example:

Then your application knows:

$account->platform

SocialAPI remains the external source for actual social operations.

SocialAPI currently supports webhook events including:

comment.received

and sends them to your HTTPS endpoint.

Your endpoint:

POST /api/webhooks/socialapi

Flow:

Instagram
   ↓
SocialAPI
   ↓
POST /api/webhooks/socialapi
   ↓
Verify signature
   ↓

   ↓

   ↓
Queue job

Do not run the AI inside the webhook request.

Very important.

20. Webhook event table

Create:

webhook_events
--------------
id
business_id

provider
event_id
event_type

payload JSON

signature_valid

processed_at
failed_at

created_at

Add unique index:

(provider, event_id)

Why?

SocialAPI retries failed webhook deliveries, so you need idempotency. Their docs specifically recommend deduplicating using the interaction/event ID.

21. Webhook security

SocialAPI signs webhook requests using:

X-SocialAPI-Signature

with HMAC-SHA256.

Your Laravel middleware/service should:

receive raw body
       ↓
calculate HMAC
       ↓
compare signatures
       ↓
reject if invalid
       ↓
store event
       ↓
queue processing

Never trust:

{
   "business_id": 123
}

just because it came in the request.

Determine the business from your mapping:

socialapi_account_id
        ↓
social_accounts
        ↓
business_id
